# Code Map languages

Proposed language support and per-language extraction/resolution rules. Research date: 2026-10-18. Owner priority:
**JavaScript/TypeScript and C# first**; further languages where they are not complicated.

## Parser assets (checked on npm, 2026-10-18)

All grammars below are MIT-licensed and their official npm packages already contain a **prebuilt `.wasm`** file, so
Oxytocin does not need Emscripten or the Tree-sitter CLI to build them. The runtime is `web-tree-sitter` 0.27.1 (MIT).

| Language            | Package and version              | WASM file(s) in the package                     | WASM size  |
| ------------------- | -------------------------------- | ----------------------------------------------- | ---------- |
| JavaScript, JSX     | `tree-sitter-javascript` 0.25.0  | `tree-sitter-javascript.wasm`                   | 0.41 MB    |
| TypeScript, TSX     | `tree-sitter-typescript` 0.23.2  | `tree-sitter-typescript.wasm`, `tree-sitter-tsx.wasm` | 1.41 + 1.45 MB |
| C#                  | `tree-sitter-c-sharp` 0.23.5     | `tree-sitter-c_sharp.wasm`                      | 5.35 MB    |
| Python              | `tree-sitter-python` 0.25.0      | `tree-sitter-python.wasm`                       | 0.46 MB    |
| Go                  | `tree-sitter-go` 0.25.0          | `tree-sitter-go.wasm`                           | 0.22 MB    |
| Java                | `tree-sitter-java` 0.23.5        | `tree-sitter-java.wasm`                         | 0.41 MB    |
| Rust                | `tree-sitter-rust` 0.24.0        | `tree-sitter-rust.wasm`                         | 1.10 MB    |
| PHP                 | `tree-sitter-php` 0.24.2         | `tree-sitter-php.wasm`, `tree-sitter-php_only.wasm` | 1.06 + 1.00 MB |

Packaging consequences:

- The grammar packages also carry native Node bindings (`binding.gyp`, `prebuilds/*.node`, `install: node-gyp-build`,
  dependencies `node-addon-api`/`node-gyp-build`, optional peer `tree-sitter`). Oxytocin needs only the `.wasm` file.
  Add the grammar packages as **devDependencies** (npm 11 does not run their install scripts unless approved in
  `allowScripts` — do not approve them) and copy the `.wasm` files at build time into `resources/code-map/grammars/`
  with a checked-in `grammars.json` manifest (package, version, file, SHA-256, license). The build fails when a hash
  differs from the manifest. Only `web-tree-sitter` is a production dependency.
- `npm run licenses:check` covers production dependencies only; `scripts/generate-notices.ts` must include the copied
  grammar licenses explicitly (from the manifest) in `THIRD_PARTY_NOTICES.md`.
- Phase 0 verifies that `web-tree-sitter` 0.27 loads every grammar's ABI (grammars were generated by different
  Tree-sitter CLI versions) and records parse throughput per language. A grammar that fails is rebuilt from its pinned
  source with the matching CLI in a documented, reproducible script, or postponed.
- Total download size for the first release (runtime + JS/TS/TSX + C#) is about 9 MB; adding Python, Go and Java adds about
  1.1 MB.

## Support levels

The UI, `MAP.md` and `oxy_code_map_status` report a level per language, so nobody mistakes file-level nodes for symbol
support:

| Level        | Meaning                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------------- |
| **Files**    | File node with language, size and line count; grouped by folder. Every text file gets at least this.           |
| **Symbols**  | Declarations with kinds, signatures, spans, export/visibility; file outline; symbol search.                     |
| **Imports**  | File/module/namespace dependencies resolved inside the project; external packages as package nodes.           |
| **Calls**    | Call and type-reference edges resolved by the rules below, with provenance; the rest reported as unresolved.   |

## Plan and complexity

| Language      | Phase | Target level | Extraction effort | Resolution effort | Main difficulty                                                                    |
| ------------- | ----- | ------------ | ----------------- | ----------------- | ---------------------------------------------------------------------------------- |
| JS/TS/JSX/TSX | 1     | Calls        | Medium            | High              | Path aliases, re-exports, workspaces, dynamic imports, JSX components.              |
| C#            | 1     | Calls        | Medium            | High              | Namespace-based resolution, partial types, overloads, `var`, extension methods.     |
| Go            | 5     | Calls        | Low               | Low–medium        | Module paths from `go.mod`; methods on receivers.                                   |
| Java          | 5     | Calls        | Low               | Medium            | Packages, wildcard imports, overloads, inheritance chains.                          |
| Python        | 5     | Imports (+ simple calls) | Low   | Medium            | Dynamic typing: most method calls stay unresolved; package roots and `src/` layout. |
| Rust          | later | Imports      | Medium            | High              | Module tree, `use` paths, macros, traits.                                           |
| PHP           | later | Imports      | Medium            | Medium            | Namespaces + Composer PSR-4 autoload mapping.                                       |
| Kotlin, Ruby  | later | Symbols      | —                 | —                 | Only on demand; grammars exist in community WASM builds, not yet audited.           |

Go, Java and Python are “not complicated” in the owner's sense: extraction is a few hundred lines each with Tree-sitter,
and their module systems are explicit enough for deterministic import resolution. They form phase 5, which depends only
on phase 1 and can run in parallel with phases 2–4. Rust and PHP need more resolution work and wait for demand.

## Common rules for every language

- One extractor module per language under `src/code-map-host/extract/<language>.ts`, producing the shared file-record
  format (symbols, import intents, call/reference intents, diagnostics). Resolution is per language family; edges never
  cross language families except through explicit configuration (none in v1).
- Configuration files (`*.csproj`, `*.sln`, `*.slnx`, `Directory.Build.props`, `go.mod`, `pom.xml`, `build.gradle(.kts)`
  as text, `pyproject.toml`, `setup.cfg`, `package.json`, `tsconfig.json`) are parsed as data. Nothing is executed, no
  package manager or SDK is called, nothing is downloaded.
- Generated folders are excluded by default per language: `bin/`, `obj/` (C#), `target/` (Java/Rust), `vendor/` (Go,
  PHP), `__pycache__/`, `.venv/`, `venv/` (Python), in addition to the global list.
- Every language ships with original fixtures (expected symbols and relations reviewed by hand), precision/recall
  numbers and determinism tests, and a short coverage description in the UI.

## TypeScript / JavaScript (phase 1)

Extensions: `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs` (`.d.ts` indexed as declarations, ranked low).

- **Symbols:** functions, arrow functions and function expressions assigned to `const`, classes, methods, getters/setters,
  fields, interfaces, type aliases, enums, namespaces, exported variables, default exports (named after the binding or
  `default`), React components (functions returning JSX are marked `component`).
- **Imports:** ES `import`/`export … from`, `import type`, `export *`, `import()` with a string literal, CommonJS
  `require('…')` with a string literal. Resolution: relative paths with extension and `index` lookup (`.ts` → `.tsx` →
  `.d.ts` → `.js` …, plus TS ESM `.js` → `.ts` mapping), `tsconfig`/`jsconfig` `baseUrl`, `paths`, `extends`, project
  references; `package.json` `exports`/`main`/`types` for workspace packages; everything else → external package node.
- **Calls/references:** lexical scopes with shadowing; calls to imported bindings, local functions, `this.method()`,
  `ClassName.staticMethod()`, `new ClassName()`, JSX `<Component>`; `extends`/`implements`. Member calls on values of
  unknown type stay unresolved (no type inference in v1).

## C# (phase 1)

Extensions: `.cs`; project files `.csproj`, solutions `.sln`/`.slnx`, `Directory.Build.props` (data only). `.razor`,
`.cshtml`, `.xaml` are file-level only in v1.

- **Projects as groups:** each `.csproj` becomes a project group (name, `RootNamespace`, `AssemblyName`,
  `TargetFramework(s)`, SDK, `ImplicitUsings`, `Nullable`). Files belong to the nearest project folder above them, minus
  `<Compile Remove>` globs (simple globs only; anything else is reported). `ProjectReference` → project-to-project edge;
  `PackageReference` → external package node. Solutions add a solution group; projects outside any solution still work.
- **Symbols:** namespaces (block and file-scoped), classes, records, structs, interfaces, enums, delegates, methods,
  constructors, properties, fields, events, indexers, operators, local functions; nested types; generics with arity in the
  ID (for example `Repository/1` for `Repository<T>`); visibility (`public`, `internal`, `protected`, `private`, `file`) instead of “exported”.
- **Partial types:** declarations of the same `namespace + name + arity` across files merge into one type symbol with
  several declaration spans; members keep their own file. Edges to the type point to the merged symbol.
- **Overloads:** method IDs carry a discriminator from parameter count and declared parameter type text
  (`Save(Order,bool)`), deterministic and independent of declaration order.
- **Namespace resolution:** for a type name used in a file, look up in order: nested/enclosing types, the current
  namespace and its parents, `using` directives of the file, `global using` directives of the project, the SDK's implicit
  usings when `ImplicitUsings` is enabled (fixed, versioned list per SDK kind, for example `System`, `System.IO`,
  `System.Linq`, `System.Net.Http`, `System.Threading`, `System.Threading.Tasks`, `System.Collections.Generic` for
  `Microsoft.NET.Sdk`), `using static`, and `using Alias = …`. Types visible through `ProjectReference` are candidates;
  ambiguities stay unresolved (never guessed).
- **References:** base lists (`extends` for the first resolved class, `implements` for resolved interfaces — decided by the
  target's kind, not by an `I` prefix), field/property/parameter/return/local declared types, generic arguments,
  `new T()`, `typeof(T)`, `nameof(T)`, attributes, `catch (T)`, `is`/`as` patterns.
- **Calls:** `M()` and `this.M()` in the same type (and base types found in the project), `Type.M()` for static calls,
  `x.M()` where `x` is a parameter, field, property or local with a declared type or `var x = new T(…)`, `base.M()`.
  Overload selection uses argument count only; if several overloads match, the edge points to the method group with
  provenance `heuristic`. Extension methods, `dynamic`, LINQ query syntax, delegates/events and DI-resolved services stay
  unresolved and are counted.
- **File dependencies:** C# has no file imports. File-to-file `references` edges are derived from resolved type
  references (file A uses a type declared in file B) and drive the Overview aggregation, exactly like `imports` in TS.
- **Known limits (documented in the UI):** source generators and code generated into `obj/`, conditional compilation
  (`#if`) — both branches are indexed and marked, `InternalsVisibleTo`, multi-targeting differences, Razor components.

## Go (phase 5)

- **Modules:** `go.mod` gives the module path; a package is a directory; `go.work` adds workspace modules.
- **Symbols:** functions, methods with receiver type, structs, interfaces, type definitions/aliases, constants, variables;
  exported = capitalised name.
- **Imports:** import path → directory inside the module or workspace; standard library and other modules → package
  nodes. `_test.go` files are tests; build tags are recorded, not evaluated.
- **Calls:** `pkg.Func()` through the import name/alias, same-package calls, `recv.Method()` where `recv` has a declared
  or composite-literal type; interface method calls stay unresolved (no implementation inference in v1).

## Java (phase 5)

- **Packages:** `package` declaration; source roots detected from `src/main/java`, `src/test/java` or the folder matching
  the package path; `pom.xml`/`settings.gradle(.kts)` modules as groups (read as text/XML, never executed).
- **Symbols:** classes, interfaces, enums, records, annotations, methods, constructors, fields; visibility.
- **Imports:** single-type, wildcard (`a.b.*`, resolved only when exactly one candidate exists) and static imports;
  same-package types without imports.
- **Calls/references:** like C#: declared types of fields, parameters and locals (`var` with `new`), static calls,
  `this`/`super`, `extends`/`implements`; overloads by argument count.

## Python (phase 5)

- **Package roots:** the project root, `src/` layout, folders listed in `pyproject.toml` (`[tool.setuptools]`,
  `packages`, Poetry `packages`) and folders with `__init__.py`; namespace packages without `__init__.py` are supported
  when they are under a detected root.
- **Symbols:** modules, classes, functions, methods, module-level assignments (constants), decorators recorded on the
  symbol; `__all__` defines exports when present.
- **Imports:** `import a.b`, `from a.b import c`, relative `from . import x`; `try/except ImportError` alternatives both
  recorded; dynamic `importlib` stays unresolved.
- **Calls:** calls of imported functions/classes and module-level functions, `self.method()` inside a class and its
  project base classes, `Class.method()`. Other attribute calls stay unresolved — Python offers no declared types to rely
  on, so the level is “Imports (+ simple calls)” and the UI says so. Type hints may later improve this.

## Validation per language

For each language: at least one realistic original fixture repository (for C#: a solution with two projects, a
`ProjectReference`, file-scoped namespaces, partial classes, global usings, implicit usings and overloads; for TS: aliases,
workspaces and re-export chains), expected-graph files, precision and recall for imports and calls, determinism
(shuffled order, CRLF, case variants), performance on a generated 10,000-file fixture, and a packaged-build smoke test
loading the grammar offline.
