Implementation base: `dd91d6a` plus stage 04 changes. This report distinguishes implemented functionality from release-validation gates. No production release has been published by this task.

- Main-service tests cover disabled startup, authorization, single initial configuration, root changes, restart, options, project removal, zero-project shutdown and deletion without re-enabling indexing. IPC refuses arbitrary roots and malformed settings.
- Reviewed resolver fixture accuracy is recorded in `2026-10-19-typescript-graph.md`; it does not establish global precision/recall.

## Reproducible packaged benchmark

Run `npx tsx scripts/code-map-benchmark.ts` on Windows. The output directory defaults to `test-results/code-map benchmark żółć/`. It contains a packaged Electron ASAR application whose only main-process task is forking utility workers; no BrowserWindow is created. The actual checkout controller, native watcher, parser thread and pinned grammars are bundled. Utility PATH is empty, Git is supplied as an explicit executable, and utility socket/fetch access is disabled. The parser reads verified local WASM assets.

The harness creates an independent Git fixture with 10,000 TypeScript modules (100,000 extracted symbols) and an independent source snapshot of Oxytocin. Making each dataset an independent repository matters: keeping an untracked fixture inside the parent repository's ignored `test-results` directory correctly excludes it from Git enumeration and would invalidate the measurement.

Each dataset gets three builds with deleted map data, followed by ten source edits and restoration. These are empty-map builds with OS caches influenced by fixture creation and previous runs, not certified cold-disk measurements. The fixture then remains open for five minutes for inactive-checkout CPU measurement. Main-process CPU usage includes worker threads; RSS is process-wide. Manifest phases currently combine reading and extraction under `parse`; they must not be misrepresented as parser-only timings. Development validation ran concurrently, so these observations are a diagnostic profile, not a controlled terminal/Git noninterference experiment.

The packaged 10k fixture completed with 10,001 files, 100,000 symbols and 210,099 edges, without failed extraction. The 9,999 unresolved calls are chained calls on unknown receiver values, deliberately outside TS/JS v1 inference.

No performance-compliance claim is made. A first optimization skips per-file disk-cache probes when no cache directory exists; this baseline predates that optimization. Its benefit has not yet been measured. Complete raw results and machine metadata: `2026-10-19-phase-1.json` (Ryzen 7 5800X, 16 logical threads, 31.92 GiB RAM; Electron 44.4.5 / embedded Node 24.21.0).

The independent Oxytocin snapshot contains 997 files, 12,579 symbols and 54,424 edges. Empty-map builds: 10.92 / 7.58 / 7.51 s (median 7.58 s; nearest-rank p95 10.92 s). Edit median/p95: 1.47 / 1.52 s. Peak RSS: 899.85 MiB; immediate post-edit RSS: 663.76 MiB (not comparable to the fixture's five-minute retained measurement). Two files have the known TSX bare-ampersand grammar recovery issue and remain visibly degraded; 7 imports and 32,156 calls remain unresolved. None of these values claims a complete runtime call graph.

Persisted bytes / canonical indexed source bytes: fixture 139,007,176 / 4,826,753 = 28.80×; Oxytocin 59,092,405 / 6,349,538 = 9.31×. This decisively fails the aspirational 5% ratio for these inputs, while staying below the safety cap. The graph and extraction records repeat long textual IDs; improving this requires representation/storage work, not removing valid relationships.

Phase evidence gives the next optimization targets. Fixture enumeration is 21.80 s initially versus 0.81–1.14 s later (OS I/O effects); combined reads/extraction are 13.53–14.38 s; resolution is 1.18–1.24 s; publication is 20.04–21.88 s. Per-record safe-directory validation, thousands of fsynced cache writes, repeated graph serialization/schema clones and simultaneous in-memory records/cache strings deserve profiling. Preserve path containment, cancellation, ownership and deterministic publication while optimizing. Re-run the benchmark after changes; do not reuse this baseline as an optimized result.

## Release gates and technical decision

- NFR-1/2/5: the current full-index architecture needs further profiling for the 10k throughput, edit-latency and memory goals. Parsing alone met a different, much narrower spike goal. The initial 50k-file / 500k-symbol / 2m-edge / 512 MiB persisted-data safety limits remain explicit and enforced; they are not promises of latency or resident memory.
- NFR-3 belongs to the MCP stage and is not measured here.
- NFR-4: five-minute inactive idle evidence is being collected. Active-checkout periodic scans and controlled terminal/Git p95 regression measurements remain pending. Passing functional E2E cannot establish the ≤10% latency threshold.
- NFR-6: a verbose JSON symbol/edge graph and extraction records can exceed the size of small, dense source files. The aspirational 5% ratio is not established by the current representation. Record actual byte ratios; retain the hard persisted-data limit and pruning rather than silently dropping edges to meet a size target.
- Multi-day dogfooding and hosted Windows CI cannot be inferred from a single local implementation session. They remain pending before a production-release readiness claim. Windows local validation and Docker Linux validation are recorded separately.

Continue implementing dependent functionality while retaining these open gates. Do not market release readiness, universal performance or token savings on the strength of the small fixtures.
